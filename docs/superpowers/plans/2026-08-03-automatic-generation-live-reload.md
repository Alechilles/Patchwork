# Automatic Generation and Confirmed Live Reload Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add elected dependency-driven automatic Patchwork regeneration and report hot reload only after correlated Hytale store/key/path/provider/hash evidence confirms the expected generated state.

**Architecture:** Add one lease-scoped `AutomaticReloadController` owned by `PatchworkRuntimeHost`. It consumes normalized source/pack events, matches them against the last successful `GenerationDependencyIndex`, debounces onto one serialized epoch, and asks administration to generate a last-known-good-preserving reload plan. Extend the existing transactional `PatchReloadCoordinator` with an elected internal trigger and a built-in watcher adapter; a separate Hytale event correlator validates engine events before completing `PatchReloadTracker` expectations.

**Tech Stack:** Java 25, Hytale 0.5.7 asset registry/store/event APIs, Java NIO atomic moves, Java scheduled executor, JUnit 5, Jimfs, Maven Wrapper and Shade Plugin.

## Global Constraints

- Only the elected standalone runtime owns automatic generation, publication, event correlation, and success reporting.
- Definition create/modify/delete triggers even when the edited file is invalid.
- Relevant exact targets, cross-asset sources, glob inventory roots, and pack registration/removal trigger reevaluation.
- Generated-pack events never trigger generation; they are confirmation evidence only.
- Source events are debounced; an event during work sets one dirty flag and causes exactly one follow-up epoch.
- Edits inside already registered archive/hash packs and ModData do not auto-trigger initially; archive/hash pack registration or removal still triggers reevaluation, and manual `/patchwork reload` remains available.
- Invalid edited definitions and target-local failures retain last-known-good generated bytes for their previously owned targets.
- Generated writes use a sibling temporary file with a non-asset extension followed by an atomic move where supported.
- A disk write is reported as generated-on-disk, never hot-reloaded by itself.
- Hot reload requires correlated pending epoch, store, key, path, generated winning provider, and expected disk hash.
- Removal requires generated-provider disappearance plus expected lower provider or expected absence.
- Overflow, stopped monitor, disabled watcher, load failure, mismatch, stale event, or timeout never reports success.
- Common assets and unknown/custom stores remain restart-required initially.
- Do not leave executors, scheduled tasks, event registrations, or monitor processes running after fence/shutdown.
- Run `./mvnw.cmd test` after source changes and `./mvnw.cmd -pl standalone -am verify` after packaging/lifecycle changes.

## Hytale 0.5.7 Evidence Anchors

- `com.hypixel.hytale.assetstore.AssetRegistry#getStoreMap()` returns the registered store map; each `AssetStore#getPath()` exposes its server directory.
- `com.hypixel.hytale.assetstore.event.RegisterAssetStoreEvent` and `RemoveAssetStoreEvent` cover dynamic stores.
- `com.hypixel.hytale.assetstore.event.AssetStoreMonitorEvent` exposes store, pack, created, modified, and removed paths before load processing.
- `com.hypixel.hytale.assetstore.event.LoadedAssetsEvent` and `RemovedAssetsEvent` expose loaded/removed asset type maps and keys.
- `AssetMap#getAssetPack()` and `AssetMap#getPath()` provide post-load winning provider/path evidence.
- `AssetModule#getAssetMonitor()` is null when `--disable-file-watcher` is set or monitor construction failed.
- `AssetEditorPlugin.setup()` demonstrates `getEventRegistry().register(Event.class, handler)` for store, pack, and monitor events.
- Directory packs are mutable/watched; archive/hash packs are immutable. Common monitor events do not provide equivalent server-store confirmation, so Common remains restart-required.

Implementation must run `mcp__hytale_workshop__validate_hytale_code_refs` on every new Hytale-facing Java file before the final packaging verification.

```java
public boolean isAffected(PatchworkSourceEvent event) {
    if (GENERATED_PACK_ID.equals(event.sourcePackId())) return false;
    if (event.kind() == PACK_REGISTERED || event.kind() == PACK_REMOVED) return true;
    if (!event.mutable()) return false;
    if (isDefinitionRoot(event.assetPath())) return true;
    if (expandedTargets.contains(event.assetPath()) || sourceAssets.contains(event.assetPath())) return true;
    return globRoots.stream().anyMatch(root -> event.assetPath().startsWith(root.stablePrefix()));
}
```
