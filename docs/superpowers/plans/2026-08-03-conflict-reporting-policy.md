# Patch Conflict Reporting and Policy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Detect overlaps between actual effects from different definitions, expose deterministic report-only diagnostics, and then add definition-level Report/Allow/Reject enforcement without changing unrelated targets.

**Architecture:** Consume `MutationEffect` records from the pure engine. Fold one definition at a time in `PatchGenerationService`: apply to a copied candidate, analyze only the new definition's effects against previously accepted effects, then accept the candidate, suppress actionable reporting, or reject the target according to the later definition's policy. Store sanitized `ConflictRecord` values on `GenerationPlan` and administration state; never expose value fingerprints.

**Tech Stack:** Java 25, Gson 2.11, Hytale 0.5.7 command API, JUnit 5, Maven Wrapper.

## Global Constraints

- A conflict is an overlap between actual effects from different definitions on the same target.
- Every successfully applied leaf write is traceable, including a value-equal write; skipped/inapplicable operations are not conflicts.
- Operations within one definition are presumed intentional and never conflict with one another.
- Reports distinguish same-pack/cross-pack and redundant-identical/material overlaps without printing values or fingerprints.
- Report-only behavior ships first and must produce byte-identical generated output.
- `ConflictPolicy` belongs to the later definition: `Report` default, `Allow`, or `Reject`.
- `Reject` stops that target's epoch, publishes no candidate, applies no later definitions, and retains previous generated bytes when available.
- Conflict failures remain target-local.
- `ConflictPolicy` is neutral-language-only; explicit format 1/2 parsing remains unchanged.
- Native Asset Editor schema, neutral portable schema/capabilities, docs, and tests ship with the policy.
- Run `./mvnw.cmd test` after code changes.

```java
public final class PatchworkConflictsCommand extends AbstractAsyncCommand {
    public PatchworkConflictsCommand(PatchworkCommandActions actions) {
        super("conflicts", "Show overlapping Patchwork effects");
        requirePermission(PatchworkCommandRoot.ADMIN_PERMISSION);
        setPermissionGroups(PatchworkCommandRoot.DEFAULT_GROUP);
        addUsageVariant(new TargetVariant(actions));
    }

    private static final class TargetVariant extends AbstractAsyncCommand {
        private final RequiredArg<String> target = withRequiredArg(
                "target", "Exact generated target path", ArgTypes.STRING);
        private final PatchworkCommandActions actions;

        private TargetVariant(PatchworkCommandActions actions) {
            super("Show conflicts for one exact target");
            this.actions = actions;
        }

        @Override protected CompletableFuture<Void> executeAsync(CommandContext context) {
            return actions.conflicts(context.get(target))
                    .thenAccept(lines -> lines.forEach(line -> context.sendMessage(Message.raw(line))))
                    .toCompletableFuture();
        }
    }
}
```

- [ ] **Step 3: Parse neutral policy only**

Add `ConflictPolicy` to the neutral root allowlist and `PatchDefinition` constructor/getters. Parsing is case-insensitive and absent means REPORT. Do not add the field to format 1/2 allowlists.

```java
private static ConflictPolicy readConflictPolicy(JsonObject root, PatchLanguage language) {
    if (language != PatchLanguage.NEUTRAL) return ConflictPolicy.REPORT;
    String value = readString(root, "ConflictPolicy", "Report");
    return switch (value.toLowerCase(Locale.ROOT)) {
        case "report" -> ConflictPolicy.REPORT;
        case "allow" -> ConflictPolicy.ALLOW;
        case "reject" -> ConflictPolicy.REJECT;
        default -> throw new IllegalArgumentException("ConflictPolicy must be Report, Allow, or Reject.");
    };
}
```

- [ ] **Step 4: Enforce the later definition's policy**

Pass `definition.conflictPolicy()` to `ConflictAnalyzer.analyze(...)`.

- REPORT: accept candidate/effects and append conflicts.
- ALLOW: accept candidate/effects but do not append its overlaps as actionable report rows.
- REJECT: if any overlap exists, do not accept candidate/effects, record a rejected-target diagnostic naming the later patch, stop applying definitions for that target, and emit no entry for that target.

Expose rejection distinctly in `PatchStatusSnapshot`. In the same task, add `LastKnownGoodPlanner.preserveRejected(priorInventory, nextPlan)`: for each rejected target already present in the prior generated inventory, copy the prior bytes into the effective next inventory before `PatchworkAdministrationService` computes manual reload updates. This makes `/patchwork reload` retain prior bytes immediately; the automatic reload plan later extends this class for invalid-definition ownership.

```java
public Map<String, byte[]> preserveRejected(
        Map<String, byte[]> priorInventory,
        PatchGenerationService.GenerationPlan nextPlan) {
    Map<String, byte[]> effective = mutableInventory(nextPlan);
    nextPlan.status().rejectedTargets().keySet().forEach(target -> {
        if (priorInventory.containsKey(target)) effective.put(target, priorInventory.get(target).clone());
    });
    return immutableCloned(effective);
}
```
